# AUD-043 — Unknown-kid JWKS refresh amplification (D-03)

**Severity:** Medium (DoS) · **Status:** Fixed (wave 8, commit betterbase-inference `0316732`).

## Finding
`JwksClient::get_key_bytes` treated a cache miss as a reason to refresh: an unknown `kid` — forgeable by any unauthenticated sender, and validated *before* the per-user rate limiter runs — always triggered an upstream fetch. Concurrent waiters serialized on the refresh mutex but each still refreshed. Additionally the 1MB size cap was checked only after `resp.bytes()` had buffered the entire body.

## Fix
- Every refresh attempt (success or failure — the stamp is taken before the fetch) records `last_refresh_attempt`; further attempts within a 30s `REFRESH_FLOOR` are refused and answered from cache (possibly stale, consistent with the pre-existing failure fallback) or as `KeyNotFound`. Unknown-kid traffic is thus bounded to one upstream fetch per window globally, and mutex waiters that observe a fresh attempt skip their own fetch.
- Oversized bodies are rejected via a `Content-Length` precheck and enforced while streaming (`resp.chunk()` accumulation) — the client never buffers an unbounded JWKS response.

## Tests
`test_unknown_kid_refresh_is_cooldown_limited` (burst of 5 unknown-kid lookups → wiremock upstream hit exactly once), `test_known_key_served_from_cache_during_cooldown` (stale-but-known key served without fetch), `test_oversized_jwks_rejected` (error names the size limit).
