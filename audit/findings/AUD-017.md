# AUD-017: Persistent OPFS database uses journal_mode=MEMORY; abrupt browser termination can corrupt previously committed data

- Type: Defect (configuration) — resolved as a deliberate tradeoff change
- State: Fixed 2026-09-21 (decision: switch to PERSIST); verified locally (browser regression pin + full SDK `just check` green)
- Owner: remediation wave 3
- Affected repositories: `betterbase` (`betterbase-db-wasm` + `js/`)
- Violated invariant: INV-01/INV-06 (crash durability of committed local data)

## Remediation (implemented)

`journal_mode=MEMORY` → `journal_mode=PERSIST` (file-backed rollback journal,
header-truncated across transactions) in
`betterbase-db-wasm/src/wasm_sqlite_backend.rs`. `synchronous=NORMAL`
retained; `temp_store=MEMORY` and `cache_size` unchanged. WAL remains
unavailable on the OPFS SAH Pool VFS.

## Decision record (performance/safety tradeoff, user-approved)

Fresh browser measurements (300 single-record puts, each its own
transaction — the UI write pattern; 300-record bulkPut in one transaction):

| journal | single put | bulk per record |
|---|---|---|
| MEMORY | ~0.82 ms | ~0.033 ms |
| PERSIST | ~2.59 ms | ~0.043 ms |

PERSIST costs ~1.8 ms per debounced UI write (3.2x) and leaves bulk /
transactional writes effectively unchanged. The prior analysis's safety
claim ("at most one in-flight write is lost") was factually incorrect:
with a RAM-only rollback journal, modified pages can reach the OPFS file
while the journal exists only in memory, so a crash mid-transaction
corrupts the database file — including previously committed data (SQLite
documents this; the audit's native crash harness reproduced it). For a
local-first database whose only copy of unsynced data is this file, the
honest trade favors PERSIST. Decision made 2026-09-21 with the
re-measured numbers.

Residual (accepted): `synchronous=NORMAL` leaves a power-loss/OS-crash
window (would require synchronous=FULL fsyncs to close); browser/process
crashes — the realistic failure modes — are covered by the file-backed
journal.

## Verification (regression tests)

- `browser-tests/db/journal-probe.test.ts`: the database opens with
  journal mode "persist" (new `Database.journalMode()` diagnostic plumbed
  through the worker boundary — wasm `journal_mode()`, worker-host
  `journalMode` case, `OpfsDb.journalMode()`).
- Existing persistence/reopen browser tests continue to pass on the new
  journal mode (full browser suite: 200/200).
