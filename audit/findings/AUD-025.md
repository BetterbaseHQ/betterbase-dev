# AUD-025: Per-space pull cursor advances before local application; decrypt failures and partial streams are silently skipped

- Type: Defect
- State: Fixed 2026-09-21; verified locally (SDK `just check`: 484 vitest incl. 10 new AUD-025 regressions, 199 browser, 1379 Rust, clippy/tsc clean)
- Owner: remediation wave 3
- Affected repositories: `betterbase` (SDK `js/`)
- Violated invariant: INV-02

## Remediation (implemented)

The per-space pull cursor is the durable re-pull gate; it now cannot advance
past work that was not delivered, decrypted, and applied:

1. **Partial streams** (`ws-client.ts`): `pull.begin` no longer adopts the
   advertised head cursor up front. The space cursor starts at `prev`,
   advances to each delivered entry's sequence, and adopts the advertised
   head only when `pull.commit` confirms the full range (count check
   unchanged). A mid-stream server error (commit skipped, `_chunks` still
   matching what was sent) now leaves the cursor at the last delivered
   entry. Wire-compatible: no protocol change; the server already sends
   `cursor` in `pull.commit` (core `ws.rs:332`).
2. **Decrypt failures** (`ws-transport.ts`): a decrypt failure at sequence N
   gates the space's staged cursor at N-1 (records below N applied; the
   failed record and everything after it are re-pulled next cycle — CRDT
   merge makes re-application idempotent). `PullResult.failures` now
   propagates from the per-space transports into `WSTransport.pull`'s
   result, so SyncManager surfaces them as sync errors (previously dropped
   at this boundary — the "silent" half of the finding).
3. **Advance-before-apply crash window** (`ws-transport.ts` +
   `sync-manager.ts`): pull cursor advances are now *staged* (neither
   memory nor the durable `cursorStore` advance) until
   `SyncTransport.commitPersistedCursors(collection)` is invoked by
   SyncManager after records are applied. An apply throw returns early —
   staged cursors are dropped by the next pull for that collection; a
   crash between pull and application re-pulls the range after reload.
   A superseded uncommitted stage cannot leak stale values (drop + restage
   per cycle, pinned by test).

Realtime fast path was already safe (advances only on zero errors) —
untouched.

## Verification (regression tests)

- `ws-client.test.ts`: partial stream without commit keeps cursor at last
  delivered entry; nothing delivered falls back to `prev`; full stream
  adopts the advertised head on commit.
- `ws-transport.test.ts`: decrypt failure mid-stream gates the cursor at
  N-1 and the next pull re-requests from the gated cursor; partial stream
  gates at last delivered; cursors stage (not persist) until
  `commitPersistedCursors`; a superseded uncommitted cycle commits only the
  latest staged value.
- `sync-manager.test.ts`: `commitPersistedCursors` called after a
  successful pull; not called when application throws; still called when
  the collection-cursor write fails (application succeeded).

## Residuals / judgement calls

- Per-record **apply** failures (post-decrypt, local DB) still advance
  cursors; they are surfaced as permanent sync errors and handled by the
  in-memory quarantine/threshold mechanism. Durable quarantine (and the
  memory-only failure maps noted in the verification chain) remains open as
  a hardening item, not part of this finding's loss window (records were
  delivered and decrypted; the loss vector is re-pull, not delivery).
- `WSTransport.pull` used outside SyncManager without calling
  `commitPersistedCursors` degrades to re-pulling each cycle (safe, not
  lossy).
