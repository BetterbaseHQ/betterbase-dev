# AUD-007: The normal recovery page consumes its one-use token twice

- Type: Defect
- State: Fixed 2026-09-21; verified locally incl. PostgreSQL-backed tests ([evidence](../evidence/2026-09-21-remediation-wave4.md))
- Severity / rationale: High — legitimate complete UI recovery cannot progress past init; a wrong phrase burns the token
- Confidence and evidence basis: source-confirmed, cross-verified
- Owner: remediation wave 4
- Affected repositories, revisions, and local patches: `betterbase-accounts` fix `d7a9671` (recovery.rs blob fetch)
- Violated invariant / linked decision: INV-05; D-004

## Impact and preconditions

The recovery page fetches the encrypted blob with the verification token (consuming the JTI), then submits the same token to recovery init (consuming it again). Storage correctly rejects the second consumption, so the real UI sequence could never complete.

## Remediation (implemented)

The blob fetch validates the token and purpose but no longer consumes the JTI — single use is enforced at the state-changing boundary (recover/init). The blob stays encrypted; re-reading it while the token is unused discloses nothing the token does not already authorize, and a wrong-phrase decrypt can now be retried with the same token.

## Verification

Route tests: blob fetch succeeds twice with one token; recover/init then accepts the token (200 with an OPAQUE response); a replayed init is rejected "verification token already used". Verifier: remediation agent, 2026-09-21.
