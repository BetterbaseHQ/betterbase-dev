# AUD-004: Refresh-token reuse does not revoke the surviving token family

- Type: Defect
- State: Fixed 2026-09-21; verified locally incl. PostgreSQL-backed tests ([evidence](../evidence/2026-09-21-remediation-wave4.md))
- Severity / rationale: High — copied refresh token keeps its replacement alive after the legitimate client presents the original
- Confidence and evidence basis: source defect plus executed PostgreSQL mechanism (pre-fix reproduction in the 2026-09-20 identity verification wave)
- Owner: remediation wave 4
- Affected repositories, revisions, and local patches: `betterbase-accounts` fix `5407abd` (oauth.rs, oauth_refresh.rs, storage trait); `betterbase` `de859ed` (cross-tab coordination)
- Violated invariant / linked decision: INV-04/05; D-004

## Impact and preconditions

Sequential reuse: an attacker who rotates a copied refresh token first keeps the replacement even when the legitimate client later presents the old token (handler answered plain `invalid_grant` without consulting `used_refresh_tokens`). Concurrent reuse: the used-hash INSERT's 23505 aborted the rotation transaction, so the family-revoking DELETE failed with 25P02 and rolled back — no revocation, old token restored.

## Remediation (implemented)

Sequential: `invalid_grant` for an unknown token now resolves the hash in `used_refresh_tokens`; a hit revokes the grant's active family and answers 401 "reuse detected". Concurrent: the used-hash INSERT uses `ON CONFLICT DO NOTHING` and detects reuse via `rows_affected`, keeping the transaction usable so the family DELETE commits. `get_used_refresh_grant_by_hash` added to the storage trait. SDK side: refresh rotation is serialized across tabs via Web Locks (per storage key); after acquiring the lock the session adopts a peer tab's rotated token instead of re-presenting the superseded one (which would now revoke the family), and treats an emptied store as logout — without this, family revocation would turn benign parallel-tab refreshes into logout storms.

## Verification

Storage tests (real PostgreSQL): sequential reuse reports `RefreshTokenReused` and deletes the surviving family; the concurrent ordering does the same despite the duplicate-insert abort; used-token lookup resolves the grant. Route tests: sequential reuse → 401 + replacement revoked; two concurrent presentations of one token → exactly one 200 and the winner's replacement dead; keypair of revoked-token semantics (400 plain invalid_grant). SDK vitest: peer-rotation adoption, empty-store logout (no network call), lock name/mode. Verifier: remediation agent, 2026-09-21.
