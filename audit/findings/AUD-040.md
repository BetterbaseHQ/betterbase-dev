# AUD-040 — Federation signing vs proxy reconstruction disagree (C-17)

**Severity:** Medium (production federation availability) · **Status:** Fixed (wave 7, commit betterbase-sync `0bb94a7`).

## Root cause
Outgoing peers sign their full configured `ws://`/`wss://` URL; incoming upgrades with origin-form URIs were reconstructed as `ws://{host}{path}` unconditionally. Behind a TLS-terminating proxy the peer signs `wss://…` while the backend rebuilds `ws://…` — the signature bases differ and verification can never succeed, despite the deployment being otherwise correct.

## Fix
`build_federation_auth_request` honors the first `X-Forwarded-Proto` hop when the operator opts in via `FEDERATION_TRUST_FORWARDED_PROTO` (default off): `https`/`wss` → `wss`, `http`/`ws` → `ws`, unrecognized values fall back to `ws`. Untrusted mode reconstructs exactly as before.

Opt-in rationale: honoring the header without a proxy lets a peer flip the reconstructed scheme, which can only cause auth failure (no forgery — the signature still must verify against the flipped base), but the explicit flag documents the deployment assumption and keeps default behavior byte-identical.

## Tests
- `websocket_federation_route_accepts_wss_signature_behind_trusted_proxy` (end-to-end over real WebSockets): a `wss://`-signed upgrade with `X-Forwarded-Proto: https` and the trust flag completes the handshake.
- `websocket_federation_route_rejects_wss_signature_without_forwarded_trust`: same request without the flag is rejected 401 (explicit opt-in).
- `forwarded_ws_scheme_maps_recognized_protocols`: multi-hop header lists, mapping table, garbage fallback.
