# AUD-014 — Email-code attempt counting and consumption not atomic (A-12)

**Severity:** Medium (race) · **Status:** Fixed (wave 11, accounts `df7af27`).

## Finding
`verify_code` ran as per-statement queries on the pool: snapshot read → attempt increment → hash compare against the *stale snapshot* → best-effort delete (results discarded). The audit **reproduced both failure modes** in isolated PostgreSQL: (a) two concurrent presentations of one correct code both succeed (B's UPDATE/DELETE hit 0 rows, errors ignored, fresh JTI minted each call so one-time-use dedup never fires); (b) concurrent wrong guesses each read `attempts=0` and the 5-attempt bound is overrun.

## Fix
New `VerificationStorage::consume_verification_code(email, purpose, code_hash, max_attempts)` — a single transaction: `SELECT ... ORDER BY created_at DESC LIMIT 1 FOR UPDATE`, expiry check, attempt-bound check (delete + `Exhausted`), guarded `attempts + 1`, constant-time compare, delete-on-success / delete-at-bound for mismatches, commit. Concurrent verifications serialize on the row lock: **at most one `Consumed` per issued code, at most `max_attempts` comparisons ever**. `api::verify_code` is now a thin mapping to the old error variants (`Consumed → Ok(id)`, `Mismatch → VerificationCodeNotFound`, `Exhausted → VerificationMaxAttempts`).

## Tests (storage-level, live PostgreSQL — the audit's own schedules mirrored)
- `consume_succeeds_exactly_once_then_row_is_gone`
- `concurrent_correct_codes_produce_exactly_one_success` (audit demo 1)
- `concurrent_wrong_codes_cannot_exceed_the_attempt_bound` — six concurrent wrong guesses: exactly five `Mismatch` outcomes, the sixth finds the row gone (audit demo 2)
- `consume_reports_exhausted_without_comparing` — past the bound, even the correct hash fails
