# AUD-036 — Interrupted uploads stuck in `uploading` forever; eviction pinned

**Audit finding (C-13):** `FileStore.processOneUpload` durably marks items `uploading` before sending; the queue scan only picks `pending`/`error`, and nothing ever resets abandoned `uploading` items — permanently excluded from retries (across restarts) with their cache allocation pinned (eviction protects any `uploadStatus`).

**Fix** (`betterbase` commit `2d0fd71`): the queue scan resets `uploading` entries whose `lastAttemptAt` is older than `STALE_UPLOAD_MS` (15 min) back to `pending`. The window is deliberately generous — `uploading` doubles as the cross-instance claim (a peer tab's scan skips it) and slow links legitimately hold large uploads for minutes — and a reset that races a live uploader is safe, not merely rare: object create-mode plus AUD-027's idempotent metadata commit mean the race loser observes an already-recorded file. Eviction protection is unchanged (their blob may be the only copy of unacknowledged bytes); the comment there now states the bounded-window reasoning.

**Regressions** (`js/src/sync/file-store.test.ts`, crash state written directly to IndexedDB):
- stale `uploading` entry is reset and uploaded on the next scan (fails pre-fix: upload never called);
- recent `uploading` entry is never stolen from a peer instance.

One timing-sensitive existing test (`disconnect reverts to local-only`) was restructured deterministically: it enqueued while a connected store was background-processing, so its outcome raced that processing; it now disconnects before enqueuing, which is the property it asserts.

**Verification:** SDK `just check` green (517 node + 200 browser); platform e2e green. **Status:** Fixed (wave 6).
