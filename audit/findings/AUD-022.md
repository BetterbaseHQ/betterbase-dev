# AUD-022: Pending auto-ID writes replayed without dedup after leader failover; ambiguous commit can duplicate inserts

- Type: Defect
- State: Fixed 2026-09-21; verified locally (SDK `just check` green incl. 4 new JS + 1 new Rust regression tests)
- Owner: remediation wave 3
- Affected repositories: `betterbase` (SDK `js/` + `crates/betterbase-db`)
- Violated invariant: exactly-once intent for auto-ID inserts across ambiguous completion (XR-01)

## Remediation (implemented)

Client-side id preallocation at the OPFS boundary:

- `OpfsDb.put` / `OpfsDb.bulkPut` preallocate a `crypto.randomUUID()` into
  the document before dispatch when the caller supplied no id (and respect
  `options.id` when present). The serialized request therefore carries a
  stable id across `RpcClient.replaceTransport` replays (failover /
  worker reconnect).
- Rust `Adapter::put` was already an upsert (existing id → update,
  auto-fields merged from the stored record, `createdAt` preserved), so a
  replayed put with the same id is an idempotent update — no second
  insert, no caller-visible id change. Pinned by a new adapter test.

Rationale for this shape: the failure mode is *uncertainty about an
already committed write*, not concurrent mutation (single leader worker).
Making the replayed request deterministic (stable id) converts the
ambiguous insert into an idempotent upsert without a durable dedup store.
General replay safety for other mutations (patches with side effects,
unique-index rejections on retry) remains as characterized — patches are
idempotent by content, and unique-constraint retries fail loudly rather
than duplicating.

## Verification (regression tests)

- `OpfsDb.test.ts`: put without id dispatches a preallocated UUID;
  the replayed request carries the identical serialized payload (same id);
  caller-supplied ids and `options.id` are never overwritten; every
  bulkPut record gets a distinct preallocated id.
- `crates/betterbase-db/tests/storage/adapter.rs`
  `put_with_existing_id_updates_instead_of_duplicating`: re-put of an
  identical document updates in place — one record, stable id,
  `createdAt` preserved.

## Residuals / judgement calls

- `updatedAt` bumps on the replayed update (inherent to upsert semantics;
  the record content is otherwise identical).
- Auto-fields are fixed top-level `id`/`createdAt`/`updatedAt` in the
  SDK's schema language (`build_full_schema`; the JS builder cannot
  declare nested `Key` nodes), so top-level preallocation covers all
  client-declarable auto ids.
