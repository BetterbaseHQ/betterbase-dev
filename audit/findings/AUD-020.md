# AUD-020 — Native read/modify/write lacks an encompassing lock

- **Register**: B-04, Defect (concurrency), High
- **Report**: `audit/reviews/02-local-data.md` §B-04 (cross-review `09` widened scope: explicit transactions do NOT hold the mutex across the closure)
- **Fixed**: 2026-09-21, wave 5

## Root cause (confirmed)

Two layers failed together:

1. `SqliteBackend::transaction` took the reentrant connection guard only around its SAVEPOINT/RELEASE statements and released it before invoking the closure — despite its own comment claiming the opposite. Nothing serialized the operation sequence inside a "transaction".
2. The adapter's single-record operations (`put`, `patch`, `delete`, `mark_synced`) each performed `get_raw` → prepare → `put_raw` as three separate backend calls with no transaction at all. Two native callers could interleave whole operations in the gaps: an in-flight patch could resurrect a completed delete; a stale acknowledgement could overwrite a newer raw record.

## Fix

- `crates/betterbase-db/src/storage/sqlite.rs`: `transaction` holds the guard across the entire closure (reentrant for the closure's own SQL; other threads block until commit/rollback).
- `crates/betterbase-db/src/storage/adapter.rs`: every single-record RMW now runs inside `self.backend.transaction(...)` via backend-parameterized cores (`put_impl`/`patch_impl`/`delete_impl`/`mark_synced_impl`); `bulk_put`/`bulk_delete` drive the cores directly so the batch composes as one savepoint instead of nesting.

Commit: betterbase `2faaf0d`.
