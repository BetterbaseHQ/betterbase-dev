# AUD-012: Browser key/session storage is not identity scoped

- Type: Defect (candidate, downstream impact pending integration evidence)
- State: Fixed 2026-09-21 (core isolation); verified locally ([evidence](../evidence/2026-09-21-remediation-wave4.md))
- Severity / rationale: High candidate — cross-tab account replacement leaves stale keys paired with new credentials; parallel logins overwrite each other's ephemeral keys
- Confidence and evidence basis: source mismatch confirmed 2026-09-20; the concrete data-loss chain remained integration-dependent
- Owner: remediation wave 4
- Affected repositories, revisions, and local patches: `betterbase` fix `06883f4` (key-store.ts scoped views + per-transaction ephemeral keys; session.ts/client.ts scoping via storagePrefix; react.ts identity reload)
- Violated invariant / linked decision: INV-04/08; D-004

## Impact and preconditions

KeyStore used one fixed IndexedDB database and fixed key IDs; two sessions with different prefixes read whichever encryption key was imported most recently, and destroying either cleared all keys. OAuth ephemeral keys used one cross-tab slot while state/verifier were tab-local, so parallel logins overwrote the other tab's decryption key. The React key-loading effect depended only on session-object identity, so an in-place cross-tab account replacement served the old account's keys with the new account's tokens.

## Remediation (implemented)

`KeyStore.scoped(scope)` namespaces every key id under `scope::`; AuthSession and OAuthClient derive the scope from `storagePrefix` (added to OAuthConfig so callback-time imports land in the session's scope), making a storage prefix real isolation. `clearAll(scope)` destroys only that scope. Legacy unscoped keys are adopted into exactly one scope (global claim marker) so upgrades keep users logged in; a second scope must re-login rather than silently share ambiguous material. Ephemeral OAuth keys are namespaced by the OAuth state (transaction). `useSessionToken` bumps an identity version on storage events and reloads keys on cross-tab replacement.

## Verification

Vitest (fake-indexeddb): scoped views hold disjoint key material; scoped destroy leaves the other scope intact; legacy adoption claims exactly once; ephemeral keys isolated per transaction. Session test: destroy clears only its own scope. SDK suites 511 vitest + 200 browser green; all example apps build/test against the change. Verifier: remediation agent, 2026-09-21.

## Residual (documented)

Two sessions configured with the SAME storage prefix still share one localStorage slot by construction (that is a pre-existing collision, not a new one); the report's "bind snapshots of credentials and keys together" (atomic credential+key commit across localStorage/IndexedDB) Closed in wave 5 (betterbase `0aa9298`) for the restore direction: keys are written to IndexedDB before the localStorage credential commit, and `AuthSession.restore` verifies the key manifest (`hasEncryptionKey`/`hasEpochKey`/`hasAppPrivateKey`) against IndexedDB, failing closed (state removed, fresh login) on any gap — covering IDB eviction with localStorage survival.
