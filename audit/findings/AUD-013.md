# AUD-013 — Refresh grants the first grant's scope, not the current authorization's (A-11)

**Severity:** Medium · **Status:** Fixed (wave 11, accounts `df7af27`).

## Finding
Code exchange minted access tokens with the *code's* scope, but the grant UPSERT left the stored grant's scope frozen at its first value and refresh minted with the *stored grant's* scope. A later narrow authorization was silently undone on every refresh (narrow→broad regain); symmetrically, legitimately-added capabilities were invisible to refresh until a new code exchange, and a capability withdrawn from the client kept flowing forever. Refresh also never consulted client policy (`validate_scopes_against_client` existed only in authorize).

## Fix (two directions)
1. **Grant scope tracks the current authorization**: both `get_or_create_oauth_grant` UPSERTs now `SET scope = EXCLUDED.scope` on conflict — every consent (authorize→code exchange) narrows/widens the stored grant, so `grant.scope` is always the latest authorization for that account+client. Safe against the consent-key bundle: the wrapped scoped key is derived from the account root key (root-version-checked at install), not from the scope string, and remains first-write-wins.
2. **Refresh re-validates client policy**: `handle_refresh_token_grant` loads the client and runs `validate_scopes_against_client(&grant.scope, &client)`; failure → `invalid_grant` ("grant scope no longer permitted for this client", reason logged server-side). A withdrawn capability forces re-authorization instead of being granted in perpetuity.

## Tests
`refresh_grants_the_latest_authorized_scope_not_the_first` (broad grant → later narrow code exchange → refresh returns narrow scope; red on parent, which returned the broad scope) and `refresh_fails_when_the_client_lost_the_capability` (grant "openid sync" vs client allowed ["openid"] → 400 invalid_grant; red on parent, which minted 200 broad).

## Documented residual
RFC 6749 §6 allows clients to *request* a narrower scope on refresh (`scope` parameter); this server ignores any such parameter (as before) and always mints the latest authorized scope — narrowing by request remains unimplemented, unchanged from before.
