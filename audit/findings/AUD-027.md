# AUD-027 — File upload retry acknowledged uploads whose metadata never committed

**Audit finding (C-04):** `put_file` returned 204 on object-AlreadyExists before attempting the metadata commit, so the retry of an interrupted first attempt (object stored, process/SQL lost before `record_file`) was falsely acknowledged; metadata-dependent downloads could never discover the file.

**Fix** (`betterbase-sync` commit `040ebcb`): the early return on `!created` is gone. Both first attempts and retries run the same idempotent commit (`commit_uploaded_file`): `Ok(Some(cursor))` commits + broadcasts + 201; `Ok(None)` is a true full replay → 204 with cursor untouched. A stale wrapped DEK now surfaces as 409 (was blanket 500) so clients re-encrypt under the current epoch. Postgres `record_file` already provided the idempotency primitive (`ON CONFLICT DO NOTHING`, rolled-back cursor bump); the HTTP layer simply never reached it on retry.

**Regressions** (`crates/api/src/files.rs` tests, handler-level with UCAN-capable stub storages):
- `retry_of_interrupted_upload_commits_metadata` — first attempt stores bytes + fails metadata (injected), retry → 201 with metadata present (the exact finding state).
- `replay_of_fully_recorded_upload_returns_204` — full replay stays 204, cursor unchanged.
- `retry_with_stale_generation_conflicts` — stale DEK → 409, nothing recorded.

**Verification:** `just check` (sync workspace incl. clippy/fmt) green; platform e2e re-run green (125 + 3 skips, faults 3/3). Reviewer's adjacent tombstone-attachment note (deletion between `record_exists` and insert) remains open as lifecycle policy, unchanged by this fix.

**Status:** Fixed (wave 6).
