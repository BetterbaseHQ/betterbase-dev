# AUD-023 — Failed OPFS init retains leadership without a usable database (XR-02)

**Severity:** Medium · **Status:** Fixed (wave 11, betterbase `607b3a6`).

## Finding
`TabCoordinator.create` stored `electionRelease` and then awaited leader/follower init; on rejection the error propagated but the caller never received the `close` function — the only path that released the Web Lock. Separately, the promoted-leader path (`onPromoted`) caught its worker-open failure with a bare `console.error`, keeping both leadership and `promoting=true`. In both cases a tab with no usable database held the lock (or a queued promotion) until page termination, blocking every other tab from opening the database. Failure sources are real (e.g. OPFS install retries exhausting after 5 attempts in the wasm adapter).

## Fix (`js/src/db/opfs/tab-coordinator.ts`)
- `create` wraps init: on failure it marks the coordinator closed and **releases the election lock** before rethrowing, so other tabs immediately become eligible to open the database.
- `onPromoted` failure path: resets `promoting`, **releases the lock** (which also ends our queued-promotion hold), and re-arms follower listening (`listenForLeaderChanges`) — the failed tab falls back to following the next healthy leader instead of wedging the page. Release-after-promotion cannot re-elect this tab (its queued lock request is done), so no failure loop.
- New `releaseElectionLock()` helper now also used by `close()` (behavior-identical, single idempotent path).

## Tests
`js/src/db/opfs/tab-coordinator.test.ts` (node pool; Web Locks/Worker/RPC seams mocked, coordinator logic real): `releases the election lock when initial leader init fails` and `releases leadership and resumes following when promotion fails` — both red on parent (release never called; no re-armed listener).

## Documented residual
If promotion fails, the tab's existing RpcClient keeps its last transport until a new leader announces; in-flight calls on the dead transport fail until the reconnect lands (same as any leader death — not specific to the failed-promotion path). Page unload always releases browser-owned locks regardless.
