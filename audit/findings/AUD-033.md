# AUD-033 — Read-only invitees cannot accept/decline (C-10)

**Severity:** Medium (functional authorization mismatch) · **Status:** Fixed (wave 7, commits betterbase-sync `0bb94a7` + betterbase `ca6f6d5`).

## Root cause
`SpaceManager.accept`/`decline` append a signed membership entry using the invitee's read UCAN; the server's `membership.append` required Write, so invitations created with `role: "read"` could complete neither path.

## Fix
- **Wire (additive, backward compatible):** `MembershipAppendParams` gains an optional `kind` field (`accept`/`decline`). Absent field — every pre-existing caller — still requires Write; unknown values fail decoding as invalid params. No route, frame-type, or error-code changes.
- **Server (`membership_append.rs`):** declared self statements authorize with `authorize_read_space`; everything else with `authorize_write_space`.
- **SDK:** `accept()`/`decline()` pass `kind` through `appendMembershipEntryWithRetry` → `MembershipClient.appendEntry` → `membership.append`.

## Boundary analysis (why read-gated self statements are sound)
The membership payload is encrypted and opaque to the server; it cannot distinguish entry classes. Privileged effect is therefore decided client-side: entries are signed and hash-chained, and clients verify a signer's authority per entry kind — an invitee's signature on a privileged claim is rejected by every verifier. The server-side gate is anti-spam/abuse defense (rate limit 10/hour retained); granting read-level append for declared self statements exposes no new effective power (write members could always append arbitrary opaque payloads).

## Tests
- `websocket_membership_append_self_statement_allows_read_ucan` (api ws tests): read UCAN + unlabelled → forbidden; read + `kind: accept` → appended; write + unlabelled → appended (back-compat).
- `MembershipClient.appendEntry` forwards the self-statement kind; unlabelled appends omit the field entirely (SDK unit test).
