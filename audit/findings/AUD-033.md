# AUD-033 — Read-only invitees cannot accept/decline (C-10)

**Severity:** Medium (functional authorization mismatch) · **Status:** Fixed (wave 7, commits betterbase-sync `0bb94a7` + betterbase `ca6f6d5`).

**Review round:** fixed a lost-wakeup race and gate asymmetry in the federation client (`200914d`); the boundary-analysis paragraph below was rewritten after review — client-side member-list display remains forgeable by read-level members (accepted residual, v1.x hardening documented).

## Root cause
`SpaceManager.accept`/`decline` append a signed membership entry using the invitee's read UCAN; the server's `membership.append` required Write, so invitations created with `role: "read"` could complete neither path.

## Fix
- **Wire (additive, backward compatible):** `MembershipAppendParams` gains an optional `kind` field (`accept`/`decline`). Absent field — every pre-existing caller — still requires Write; unknown values fail decoding as invalid params. No route, frame-type, or error-code changes.
- **Server (`membership_append.rs`):** declared self statements authorize with `authorize_read_space`; everything else with `authorize_write_space`.
- **SDK:** `accept()`/`decline()` pass `kind` through `appendMembershipEntryWithRetry` → `MembershipClient.appendEntry` → `membership.append`.

## Boundary analysis (corrected after independent review)
The membership payload is encrypted and opaque to the server; it cannot distinguish entry classes. The server-side gate is therefore anti-spam/abuse defense (rate limit 10/hour retained), **not** a privilege boundary — privileged effect lives elsewhere:

- **Server-side capabilities are unaffected:** push/subscribe/admin operations validate UCAN chains rooted at the space root key (`authz.rs` → `validate_chain`); a forged membership log entry mints no server capability.
- **Client-side verification is signature-consistency only:** `verifyMembershipEntry` checks that the entry is validly signed by the UCAN's issuer (`d`/`r`) or audience (`a`/`x`) — it does **not** validate that a `d`-entry signer's authority chains to the root. Consequently any holder of a valid read UCAN (and, since invitations carry the space key + read UCAN, even an unaccepted invitee) can append self-issued delegation entries that render as `admin`/`joined` in other members' **member-list display**. Write members already had exactly this power pre-fix; wave 7 widened the appender set, it did not create the hole.
- **No capability is derived from the log client-side:** sync authorization uses the locally stored space record's UCAN chain, not log-derived delegations; `handleRevocation` independently probes the server (403) before acting on a revocation.

**Accepted residual, documented:** member-list display forgery by read-level members. Recommended v1.x hardening: `parseMembershipLog` should require `d`/`r` entry signers' UCAN proof chains (`prf`) to validate against the space root public key (full client-side `validate_chain` equivalent).

## Tests
- `websocket_membership_append_self_statement_allows_read_ucan` (api ws tests): read UCAN + unlabelled → forbidden; read + `kind: accept` → appended; write + unlabelled → appended (back-compat).
- `MembershipClient.appendEntry` forwards the self-statement kind; unlabelled appends omit the field entirely (SDK unit test).
