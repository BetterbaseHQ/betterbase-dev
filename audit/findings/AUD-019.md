# AUD-019: Acknowledgement guard ignores metadata-only changes; an old ACK can clear a newer routing-metadata edit

- Type: Defect
- State: Fixed 2026-09-21; verified locally (SDK `just check` green: 498 vitest, 199 browser, full cargo/clippy)
- Owner: remediation wave 3
- Affected repositories: `betterbase` (`betterbase-db` crate + `js/`)
- Violated invariant: INV-01

## Remediation (implemented)

`PushSnapshot` now carries the record's `meta` as of the pushed read
(optional, `serde(default)` — older callers unchanged), and
`prepare_mark_synced`'s stay-dirty guard treats a mismatched meta like a
grown patch log or a flipped deleted flag: a stale in-flight
acknowledgement can no longer clear a newer metadata-only change. Both
push paths snapshot meta (JS `SyncManager.pushImpl` and the native
`sync::manager`).

The acknowledgement's `sequence` stamping is unchanged: for a record that
stays dirty, the stamped sequence represents the server position of the
acknowledged push (same pre-existing behavior as the patches-grew case);
the newer change is re-pushed and re-sequenced.

## Verification (regression tests)

- `tests/storage/record_manager.rs`
  `prepare_mark_synced_stays_dirty_when_meta_only_change_landed_after_snapshot`:
  meta A→B after the snapshot → stale ack keeps the record dirty with the
  newer meta; matching meta acks cleanly; legacy snapshots without meta
  keep the previous behavior.
- Existing `prepare_mark_synced` tests updated for the new field and still
  pass.

## Residuals / judgement calls

- Native-simultaneous-caller interleaving (B-04, no encompassing
  transaction for multi-op native sequences) remains a separate open
  finding; this fix closes the sequential snapshot-order defect as
  reported.
