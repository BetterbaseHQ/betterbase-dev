# AUD-039 — Record deletion never schedules file-object removal (C-16)

**Severity:** Medium (storage retention/capacity) · **Status:** Fixed (wave 7, commit betterbase-sync `0bb94a7`).

## Root cause
Record tombstoning deleted file metadata rows and returned `deleted_file_ids`, but no handler consumed them; the object-storage layer exposed no delete, and no GC existed anywhere in the service. Encrypted objects were retained indefinitely — inaccessible through metadata but forever allocated.

## Fix (two-phase, crash-safe)
1. **Queue (transactional):** `push` inserts tombstoned file ids into the new `pending_file_deletions` table *in the same transaction* as the metadata cascade — a crash between tombstone and queue cannot leak the object.
2. **Sweep (background):** a 15-minute task (`file_gc_loop`) deletes objects whose grace period (`FILE_DELETION_GRACE_SECS`, default 24h) has elapsed. Rows complete only after the object is gone, so backend failures retry on the next pass.
3. **Re-upload guard:** before deleting, the sweep re-checks file metadata; a client that re-created the same `(space, file_id)` after the tombstone makes the object live again — the queue entry is dropped and the object survives.

The grace window covers in-flight downloads and the PUT-retry path (bytes-before-metadata ordering). File metadata rows are unique per `(space, file_id)` (PK), so no cross-record object sharing exists to refcount.

**Accepted residual (review):** metadata could in principle be re-created in the milliseconds between the sweep's `file_exists` check and the object deletion (same-id re-upload landing exactly then, ≥24h after the original tombstone) — leaving a live metadata row pointing at a deleted object; the failure mode is a recoverable GET miss, not corruption. Narrowing further would need a post-delete existence re-check + re-queue; documented rather than fixed.

## Tests
- `push_tombstone_queues_file_deletion_in_transaction` (storage, real PostgreSQL): queue visible immediately after push; cutoff-window semantics; completion removes the entry; re-scheduling is idempotent.
- `sweep_removes_due_objects_and_completes_rows` / `sweep_spares_reuploaded_files` (api): due objects deleted + rows completed, not-yet-due untouched; re-uploaded file ids spared with queue entry dropped.
- App config: grace parsing defaults to 24h, rejects zero/garbage.
