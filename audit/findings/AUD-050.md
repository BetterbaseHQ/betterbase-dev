# AUD-050 — Chat attribution trusts writable senderHandle (E-06)

**Severity:** Medium (trust) · **Status:** Fixed (wave 9, commits examples `1750bd5` + `591bff0` review round; SDK `454be3e`).

## Finding
The chat UI's sender attribution and green shield derived from `senderHandle` — ordinary writable content. `_editChainValid` proved only chain *integrity*, not identity: any write-capable member could validly sign a message naming another member's handle and get a green shield beside the spoofed name. No comparison between chain author and claimed handle existed.

## Fix
`ChatView` resolves each message's cryptographic author — the **first** edit-chain entry's did (the record's creator; later entries are edits and don't re-attribute) — through the space's member registry (`useMembers`, fed by the verified membership log). A did that is signature-bound (the SDK's `verify_edit_entry` derives the did from the entry's signing key), mapped to a handle:
- **verified shield** only when the chain passed integrity verification *and* the resolved handle equals the claimed handle;
- **amber warning** (`ShieldAlert`) when the chain is valid but its author maps to a different handle — no silent green shield for forgeries;
- display name prefers the crypto-resolved handle;
- a peer writing under the local user's handle renders as theirs, not ours.

Review round: attribution now derives **only from chains that passed `_editChainValid`** — a tampered chain cannot drive display attribution (it falls back to the claimed handle, no shield). SDK testing double gained `setSpaceMembers` for the did→handle mapping.

## Tests
`AUD-050: shield requires the chain author's member handle to match the claimed sender` — red on parent (which rendered green shields for the spoofed and unsigned cases): asserts exactly one verified shield, one warning, across legit / spoofed / chain-absent messages. Double-fire and draft-preservation covered under AUD-051.

## Documented residuals (review)
- **Degradation windows**: messages not yet synced have no chain (claimed handle, no shield — pre-existing display); while membership is unresolved (first view before `getMembers` lands) the shield is suppressed and a spoof-as-local message transiently renders as own. Both transient, no worse than baseline.
- The raised bar is: spoofing now requires **forging membership-log signatures** (or the platform-wide AUD-033 display-forge residual), not a single field write. Not a cryptographic identity guarantee.
- Handle comparison is exact string equality between membership-log and session handles; handle immutability is a dependency (case divergence would mis-warn).
